# 开发测试闭环

本规则适用于所有功能开发、行为修改和缺陷修复。完成的定义不是“代码看起来正确”或“能够编译”，而是目标行为经过自动测试，并在涉及系统能力时经过真实应用验收。

## 1. 开工前先定义行为

先写出用户可观察的验收标准，以及要从哪个公开边界验证。优先使用真实公开接口，例如模块导出、Rust command/API、事件协议、持久化后的重新读取和可见 UI 行为；避免测试私有函数或只断言内部调用次数。

每个改动至少检查以下场景类别，并把适用项写成测试用例：

| 类别 | 必查内容 |
|---|---|
| 正常流程 | 典型输入能完成完整任务，输出和状态符合产品行为 |
| 边界情况 | 空值、最小/最大值、长度上限、队列容量、首次/末次、重复操作、快速连续操作 |
| 异常输入 | 缺字段、错误类型、非法枚举、畸形协议、过长内容；应拒绝或安全归一化，不能崩溃 |
| 依赖失败 | 网络超时、服务不可用、权限拒绝、文件缺失、进程退出、存储失败 |
| 生命周期 | 取消、重试、断线重连、窗口关闭/重开、设置热更新、旧事件迟到、跨会话隔离 |
| 平台差异 | macOS/Windows、WebView/WebView2、缩放与多显示器、开发包与安装包资源差异 |
| 安全与隐私 | 密钥、文本、PCM、路径和设备信息不进入日志、诊断或不允许的请求 |

不适用的类别无需凑测试，但高风险场景被跳过时要说明原因。

## 2. 按垂直切片执行 Red -> Green

每次只推进一个可观察行为：

1. 先增加一个会失败的测试，并运行它。
2. 确认失败来自尚未实现的目标行为，而不是测试语法、环境或夹具错误。
3. 只实现让该行为通过所需的代码。
4. 重跑该测试直到通过。
5. 再添加下一个正常、边界或异常场景。

缺陷修复必须先用测试稳定复现缺陷，再修改生产代码。只有无法自动化的原生系统行为可以先写可重复的实机步骤，同时应把可抽离的状态机、协议和纯逻辑下沉为自动测试。

测试应验证行为而非实现细节。禁止通过删除测试、放宽正确的断言、无依据增加等待时间或把真实依赖全部 mock 掉来获得绿色结果。

## 3. 分层验证

### 单元测试

开发中持续运行最窄的相关测试。纯 JS 状态和 UI 控制逻辑放在 `tests/*.test.js`；本地实时服务的纯状态、协议和回放放在 `tests/test_*.py`；Rust 解析、归一化、状态和持久化逻辑放在相应模块的 `#[cfg(test)]` 中。

### 集成测试

凡是跨模块或跨进程边界的改动，应验证完整合同，而不仅是两侧各自的单元测试。重点包括：

- 前端与 Rust IPC command/event 的字段、默认值和错误行为；
- HTTP/SSE/WebSocket 请求响应、协商、取消和迟到消息；
- 设置保存后重新加载、数据库写入后通过公开接口读回；
- Python 服务与 Rust/前端共享常量、资源清单和协议版本；
- 上游同步模块与桌面代理的契约兼容性。

提交完成前运行完整自动化门禁：

```bash
npm run test:gate
```

该命令依次执行 JS、Python、VAD 资源合同、Rust 单元测试和 Rust 编译检查。任一步失败都表示门禁失败。

### 端到端与实机验收

当前仓库没有能够可靠覆盖 Tauri 原生窗口、系统托盘、全局快捷键、麦克风权限和实时音频的自动化 E2E 驱动。因此，只要改动触及这些能力，就必须用 `npm run dev` 在受影响平台运行真实流程；资源或打包行为还必须从对应安装包验证。

实机验收仍按同一组场景执行：正常完成一次；测试相关边界；注入权限拒绝、断网/服务退出或错误输入；验证取消、重试和重开后的恢复；检查没有重复动作、卡死、残留音频或旧状态污染。涉及跨平台代码时，不能只在一个平台验收后宣称全部平台通过。

## 4. 失败后继续修复

发现失败后保持闭环：

```text
失败 -> 缩小到稳定复现 -> 判断产品缺陷或测试/环境缺陷
     -> 修复 -> 重跑最窄测试 -> 重跑受影响测试层 -> 重跑完整门禁
```

对偶发失败先固定随机性、时钟、调度或外部依赖，找到可重复原因；不得简单重跑到偶然通过。遇到当前机器无法执行的平台、账号、硬件或模型测试时，明确记录“未运行”、原因和仍需执行的命令/步骤。

## 5. 完成交付时必须报告

最终交付说明至少包含：

- 新增或更新了哪些行为测试，以及覆盖的正常、边界和异常场景；
- 实际运行过的自动测试命令及结果；
- 实际执行过的 E2E 平台和场景；
- 未运行的测试及原因；
- 仍存在的已知风险。

没有执行证据时只能说“未验证”，不能说“应该没问题”。静态代码审查、类型/编译检查和 Skill 输出都只是辅助手段，不能代替上述闭环。
