# 共同体验陪伴模式路线图

> 状态：M1.1 画面 + 音频共同体验实现中
> 日期：2026-09-05（本轮实现决策覆盖早期探索假设）
> 适用场景：看片、短剧、游戏、音乐、阅读
> 相关能力：[实时语音路线图](./roadmap-realtime-voice.md)、[Memory Brain 路线图](./roadmap-memory-brain.md)、[AI 角色扮演路线图](./roadmap-ai-roleplay.md)

> 术语边界：本文的 **Shared Experience Session（共同体验会话）** 会在用户授权后观察指定内容。长时间挂着、默认按住说话且不观察屏幕/系统音频的功能是独立的 [Background Companion Call（后台陪伴通话）](./spec-background-companion-call.md)。未来可以显式组合两者，但启动任一会话都不能静默开启另一个。

## 结论

本项目可以从“随时可聊天的桌宠”扩展为“与用户共同经历内容的 AI 角色”：在用户明确开启后，角色理解指定窗口、应用音频、用户语音和必要的媒体元数据，在合适的时机讨论剧情、玩法、歌词或书中内容。

这个功能的难点不是让多模态模型描述屏幕，而是同时满足以下三个产品条件：

1. **成本有上限**：不能持续上传画面或把整场内容反复放进上下文。
2. **能区分用户和媒体**：电影对白、游戏语音、音乐与角色自己的 TTS 不能被误认为用户发言。
3. **响应足够快且不打扰**：用户提问需要迅速回应，主动评论则必须避开对白和操作高峰，并允许保持沉默。

推荐把能力实现为显式开启、有界、会话级的 **Shared Experience Session（共同体验会话）**。第一版只做“用户主动提问 + 最近内容理解”，验证成本、声源分离和延迟后，再逐步增加低频主动评论。不要在第一版同时承诺持续视觉理解、扬声器环境自由插话和高频主动发言。

本文记录初步产品与技术判断，不代表平台采集 API、模型成本、跨平台能力或真实延迟已经验证。实现前应补充针对 macOS、Windows 和当前模型账号的原型数据。

## 当前实现决策（2026-09-05）

本节优先于本文较早的探索性假设，作为当前实现的指导依据。

### 固定模型链路

当前测试不更换模型：

```text
文字回复：DeepSeek 在线 API
视觉理解：Mage-VL
视频音频 ASR：SenseVoice2
语音合成：VoxCPM2
```

共同体验先在现有文字聊天中验证，但文字聊天默认会触发语音回复，因此第一阶段必须同时测量 `Mage-VL + DeepSeek + VoxCPM2` 的显存压力、首音频延迟、实时率和聊天窗口流畅度。SenseVoice2 接入视频系统音频后，形成完整的文字共同体验链路。实时通话的目标链路同样是 `DeepSeek API + 本地 SenseVoice2 + 本地 VoxCPM2`；不能把火山端到端服务当作共同体验或实时通话的产品依赖。仓库中现有 Volcano adapter 仅作为兼容/历史实验路径保留，不得被新功能隐式选中。

### 内容理解优先级

共同体验的优先级固定为：

```text
整体内容理解准确性 > 当前画面准确性 > 回复实时性
```

因此允许角色在回答前等待积压的视觉/音频事件完成整理。为了降低体感延迟，界面必须明确显示“正在整理刚才的画面和声音”，但不能用泛化常识替代尚未完成的观察。

### 采集与推理解耦

用户输入文字或未来在实时通话中说话时，采集不得停止：

```text
画面：继续按约 3 秒采集并记录时间戳
音频：继续切分并记录时间戳
视觉/ASR 推理：可暂缓，任务进入有界待处理队列
```

停止输入后按时间顺序处理积压内容，不得只保留最新一帧。原始图片和音频属于短期处理数据，获得视觉描述、ASR 文字和阶段摘要后即可释放；工作区只保留结构化事件、少量最近上下文和滚动总结。

### 30 分钟是分段上限，不是会话上限

共同体验可以持续超过 30 分钟。每 30 分钟建立一个新的 segment：

1. 生成该段的视觉、音频和聊天总结。
2. 将段总结合并进整个会话的滚动总结。
3. 释放该段已经完成处理的原始截图和音频。
4. 继续使用同一个共同体验会话观察下一段。

停止共同体验时，再生成一次最终总结。最终总结可以按现有 Memory Brain 的 episode 流程写入长期记忆，使普通模式之后能够记得“上次一起看了什么、大概发生了什么、用户关注什么”。原始截图、音频、完整 ASR 原文和逐帧视觉描述不得写入 Memory。

### 当前阶段边界

截至 2026-09-06，M1.2 会话闭环已实现。`SharedExperienceWorkspace` 提供音频/画面/聊天时间线和默认 30 分钟 segment rollover；`SharedExperienceSpool` 对画面/音频采集提供有界、按时间排序的暂存；`SharedExperienceLifecycle` 单飞阶段总结与停止总结，按类别记录 DeepSeek token、官方余额快照和估算费用，并在预算耗尽时让阶段 rollover 降级为本地有界压缩。阶段和最终总结从带 source id 的 Evidence Journal、已经过同一证据约束压缩的 Evidence Blocks 及用户明确确认重新归纳；不得递归压缩角色先前回答或仅基于上一版概述继续扩写，以免早期假设逐段漂移成事实。

解说视频采用独立的证据策略。用户确认标题含“解说、讲解、盘点、速看、剧情梳理”等信号时，SenseVoice2 ASR 是剧情进展、人物关系和因果的主证据；Mage-VL 只补充明确可见的场景、动作、字幕和视觉变化。解说与剪辑画面不要求逐秒同步，单帧对不上不构成冲突；自动提问不得反复要求比较声画，角色也不得机械复述“声音说了什么、画面显示什么”。视觉提示禁止凭模型常识猜作品名或角色名；除非画面文字清楚显示，否则只使用外观或身份代称。用户确认标题和无剧透 Content Primer 可校正作品身份，但不证明未播放剧情已经发生。

Content Primer 的网络搜索授权只能来自共同体验聊天中的显式用户声明，例如“我们在看《雾城旅人》的解说视频”或“我们一起看《星海纪事》电影”。窗口标题、选择器元数据和测试环境中的内容标题都不能触发 Tavily；每个会话最多尝试一次，关闭 Web Grounding、provider 不匹配、代理未就绪或请求失败时均 fail closed。测试钩子也必须把这句话作为 `userViewingStatement` 走真实发送路径，不能直接把环境变量标题伪装成用户确认。

普通电影的人物连续性使用独立的会话级匿名轨迹。初次出现分配 `person-N + 外观描述`；只有相邻镜头中描述稳定时允许标为“暂定同一人”，字幕、SenseVoice2 ASR 或用户明确确认后才可绑定名字并标为“已确认”。单帧 Mage-VL 猜测的名字永远不能提升身份状态，外观相似也不能跨长时间或切镜直接合并。当前实现不宣称具备人脸识别准确率；需要更强的跨镜头重识别时，应另行验证本地人物 embedding、多帧对比、遮挡和多人相似外观数据集。

Mage-VL/MLX 接口可以一次接收多张按时间排序的图片，现有 sidecar 的 `/observe-video` 会从短视频抽取最多 4 帧并概括粗粒度变化；但共同体验产品路径当前仍调用单帧 `/observe`。多帧可用于“出现、消失、场景切换、明显动作变化”，不能替代光流、目标跟踪或人物重识别。后续启用前须对相邻 2--3 帧窗口实测变化准确率、推理延迟、积压和统一内存，并让输出保持结构化的“保持/出现/消失/动作变化 + 不确定状态”。

用户可见回复必须像朋友陪看一样直接讨论内容。Evidence anchor、来源和不确定性保留在内部工作区；除非用户追问依据或出现会改变判断的重要冲突，不主动说“这句是……”“具体是什么还没揭晓”“声音说……画面显示……”等审计式套话。自动验收报告对这些固定模式做零容忍统计，命中即不能自动判为通过。

共同体验文字请求保留 persona、安全规则、本次聊天历史和共同体验工作区，但关闭普通 Memory recall/graph、Fresh Topics、Web Grounding、few-shot、旧 session recap、空闲主动分享及自动 follow-up。共同体验聊天原文不会进入普通 Memory 巩固队列；停止时只有 DeepSeek 最终总结通过窄 IPC 写入一个幂等 episode。最终总结失败时 fail closed，不会用 ASR/逐帧时间线 fallback 写 Memory。窗口关闭或取消会中止迟到写入，停止后的 spool、截图、WAV 和工作区状态均清理。

2026-09-05 在 `MacBook Pro (Mac16,7) / Apple M4 Pro / 48 GB` 上完成开发版短时真实验收：共同体验明确绑定到用户选择的抖音窗口；模拟输入期间计数从零增长到采集 `V2/A1`、处理 `V0/A0`、积压 `3`，证明采集继续而 Mage-VL/SenseVoice2 推理暂停；恢复后主动排空到处理 `V10/A10`、积压 `0`，画面与 ASR 结果按采集时间进入同一时间线。真实 DeepSeek 提问能够引用当时的古风视频内容，并在音频证据不足时保留不确定性；本轮共同体验 debug 聚合为 `3` 次请求、约 `7.86k` tokens，DeepSeek 余额接口从 `CNY 10.45` 变为 `CNY 10.44`（接口仅提供两位小数，因此只能确认约 `CNY 0.01` 的余额变化）。VoxCPM2 收到真实 `/tts` 请求，观测到 `33`、`38`、`60` 字片段分别约 `7.77s`、`7.15s`、`8.12s` 完成。聊天窗口被隐藏时采集和推理按产品规则暂停，重新显示后恢复；退出 Tauri 后 Mage-VL、VoxCPM2 和音频 helper 均被清理。该记录是端到端 smoke 与恢复路径验收，不替代前述受控 5--10 分钟对照实验和独立 30 分钟连续分段测试。

    -> 本地 SenseVoice2（用户语音识别）

第二阶段才接入实时通话中的用户麦克风、声源分离、实时 ASR 和通话时序，且复用上述 DeepSeek + 本地 SenseVoice2 + VoxCPM2 链路。第一阶段不因为文字输入而伪造用户语音；新实现不应依赖 Volcano WebSocket。

### 暂停观看

暂停是会话内的可逆状态，不等同于结束：

- 暂停按钮停止截图定时器、视觉/ASR 推理和新增后台模型任务；
- 已有时间线、段落总结、聊天历史和窗口选择保留；
- 恢复后从当前窗口继续采集，不重新创建会话；
- 用户输入“等下我去拿外卖”“马上回来”“先暂停一下”等明确暂离表达时，可以自动进入暂停状态，但仍照常处理这一条文字消息；
- 停止按钮才会结束会话、生成最终总结并释放临时工作区。

暂停期间若产品需要保证内容连续性，采集器可以继续写入有界 session spool，但不得执行模型推理；文字版 M1 默认先暂停采集和推理，实时通话阶段再启用“采集不停、推理暂停”的策略。

### DeepSeek 费用测量

DeepSeek 是在线 API，所有共同体验测试必须同时记录 token 和费用。现有聊天用量调试信息可以复用，但共同体验需要单独聚合：

```text
普通回复 token/费用
共同体验回复 token/费用
阶段总结 token/费用
最终总结 token/费用
每分钟 / 每 30 分钟 / 每小时累计费用
```

测试时固定记录模型、prompt tokens、completion tokens、总 tokens、请求次数、失败重试次数和 DeepSeek 余额变化。视觉、ASR、TTS 的本地资源消耗与 DeepSeek 在线费用分开统计，不能用本地显存压力替代 API 成本结论。达到用户配置的费用预算后，继续保留已采集的本地时间线，但暂停非必要的阶段总结和主动请求，并明确显示节省状态。

## 1. 产品目标

### 1.1 希望形成的体验

- **看片 / 短剧**：理解最近发生的剧情、人物关系和明显伏笔；默认不剧透未播放内容。
- **游戏**：理解任务、对话、战斗结果和重复失败；根据用户选择提供陪伴、轻提示或直接攻略。
- **音乐**：结合曲目元数据、歌词和播放进度聊情绪、歌词与编曲；尽量不依赖连续截图。
- **阅读**：围绕用户选区、当前页或章节摘要讨论观点、人物和线索；用户确认后才形成读书笔记或长期记忆。

角色不应成为持续描述屏幕的旁白。理想节奏是：持续低成本观察，只保留少量事件；用户提问时快速回答；主动发言必须同时满足“内容值得说”和“现在适合说”。

### 1.2 非目标

第一阶段不追求：

- 理解整部作品的每一个镜头、台词或游戏状态；
- 在扬声器外放环境下百分之百准确地识别用户自由插话；
- 自动获取或保存影视、音乐、书籍的大段受版权保护原文；
- 将原始截图、媒体音频、OCR 全文或外部作品内容写入 Memory；
- 为所有播放器、游戏和电子书应用提供专用集成；
- 在没有用户明确开启和选择目标窗口时观察桌面。

## 2. 核心交互模型

共同体验会话应有清晰、持续可见的生命周期：

```text
用户选择模式与目标窗口
        |
        v
显式开始采集
        |
        v
本地变化检测 / 音轨分离 / OCR / 元数据读取
        |
        v
生成少量结构化事件并维护滚动状态
        |
        +--> 用户提问：优先用已有状态快速回答，必要时异步回看关键帧
        |
        +--> 主动候选：通过价值、时机、冷却和打断门控后才播放
        |
        v
用户结束会话，立即停止采集并清除原始临时数据
```

建议提供以下明确控制：

- 模式：看片、游戏、音乐、阅读；
- 对象：用户手动选择的窗口或应用；
- 发言风格：安静、标准、活跃；
- 提示强度：不提示、轻提示、直接提示，仅游戏/剧情场景显示；
- 防剧透：默认开启，只允许讨论已观察到的内容；
- 输入方式：快捷键按住说话、唤醒后说话、耳机自然对话；
- 立即静音 / 暂停观察 / 结束会话。

## 3. 有界的感知与上下文架构

### 3.1 不持续调用大模型

固定间隔上传截图会产生大量重复视觉请求。例如每 5 秒一次，一小时就有 720 次视觉请求，因此不能作为默认架构。

推荐先在本地将连续媒体压缩为事件：

```text
视频帧 --> 感知哈希 / 画面差异 / 镜头切换 ----+
字幕区 --> OCR / 去重 / 时间合并 ----------------+--> 关键事件选择器
应用音频 --> 活动区间 / 静音空档 / 媒体 ASR ----+
播放器 --> 曲目、进度、章节等可用元数据 --------+
                                                    |
                                                    v
                                      少量关键帧 + 新增文本
                                                    |
                                                    v
                                           多模态语义事件
```

本地预处理不应自行声称理解剧情，只负责变化检测、去重、裁剪和固定规则筛选。模型返回的内容也应先进入会话级事件层，而不是直接进入 Memory。

### 3.2 会话状态

建议维护固定上限的 `SharedExperienceSession`，概念字段如下：

```ts
type SharedExperienceSession = {
  mode: "watch" | "game" | "music" | "read";
  sourceKind: "window" | "application" | "selection";
  recentEvents: ExperienceEvent[];       // 固定数量、短文本
  rollingSummary: string;                // 固定字符或 token 上限
  openQuestions: string[];               // 少量未决线索
  mentionedEventIds: string[];            // 会话内防重复
  lastUserInteractionAt: number;          // 单调时间语义
  lastAssistantPlaybackCompletedAt: number;
  budget: SessionBudget;
};
```

原始帧和音频只允许进入短期环形缓冲，用于用户询问“刚才发生了什么”时回看；默认不落盘。滚动摘要替换旧事件后，不再把旧截图或字幕重新发送给模型。

### 3.3 模式差异

- **看片 / 短剧**：字幕变化、镜头切换和人物/场景变化是主要信号。
- **游戏**：画面变化通常过于频繁，应优先识别 UI 区域、任务文本、对话框、死亡/胜利等稳定事件；以后可增加特定游戏插件，但不能作为第一版前提。
- **音乐**：优先使用操作系统媒体会话和播放器元数据；视觉只作为缺少元数据时的降级路径。
- **阅读**：优先使用用户选区、剪贴板或明确导入的当前页文本；OCR 只处理当前可见页，不持续翻取整本内容。

## 4. Token 与调用成本控制

### 4.1 成本来自哪里

共同体验模式至少可能产生四类模型消耗：视觉理解、媒体内容 ASR、滚动摘要、角色回复。最大风险通常是重复视觉分析和不断增长的历史，而不是角色最终说出的几句话。

成本必须由 App 的确定性预算控制，不能只在 prompt 中要求模型“少用 token”。建议预算至少包含：

- 每分钟视觉调用上限；
- 每小时视觉调用上限；
- 单次输入图片数量和尺寸上限；
- `recentEvents` 数量与单项字符上限；
- `rollingSummary` token 上限；
- 每小时主动发言次数；
- 单次主动回复字符或语音时长上限；
- 达到预算后的固定降级行为。

达到视觉预算后，应继续保留本地 OCR、元数据和用户主动提问能力，并显示固定的节省状态；不能静默突破预算。用户主动提问可以拥有独立的小额保留预算。

### 4.2 初始档位假设

以下数值只用于原型，不是最终承诺：

| 档位 | 视觉语义分析 | 主动发言 | 目标 |
| --- | --- | --- | --- |
| 安静 / 节省 | 每分钟最多 1 次 | 每小时最多 3--6 次 | 长电影、阅读、后台陪伴 |
| 标准 | 每分钟最多 2--3 次 | 每小时最多 6--12 次 | 普通影视和游戏 |
| 活跃 | 关键事件触发，仍有硬上限 | 每小时最多 12--20 次 | 短剧、直播式内容 |

这些上限必须经过真实一小时会话测量后再调整。实现阶段需要记录无内容的固定计数与延迟聚合，但不能把截图、字幕、曲名、作品名或用户问题写入诊断报告。

### 4.3 后续降低成本的方向

- 感知哈希、字幕去重和 UI 区域检测全部本地执行；
- 同一镜头只传一张代表帧，必要时只裁剪字幕或关键区域；
- 使用小模型做事件筛选，大模型只处理歧义或用户明确提问；
- 本地 Ollama VL 可作为可选视觉后端，但必须单独验证速度、显存和准确率；
- 角色回复只接收结构化事件和滚动摘要，不接收完整原始观察历史；
- 音乐和阅读尽量走结构化元数据或文本路径，避免视觉调用。

## 5. 区分用户语音与播放器声音

### 5.1 首选：采集时分轨

不要先混合再让模型猜声源。目标架构应从采集层保留至少三条逻辑音轨：

```text
指定应用 / 系统播放音频 --> 媒体参考轨
麦克风输入               --> 用户候选轨
角色 TTS 输出             --> 角色参考轨
```

媒体参考轨用于理解当前内容，也用于消除扬声器回灌；角色参考轨用于防止元元听见自己的 TTS。具体采集能力和授权体验需要分别验证 macOS 与 Windows，不能仅凭 API 存在就宣称可以稳定按应用分轨。

### 5.2 用户候选判定

建议采用分层判定，而不是只依赖 VAD：

1. 麦克风 VAD 发现语音候选；
2. AEC 使用媒体轨和角色 TTS 轨作为参考，抑制对应回声；
3. 比较候选与参考轨的时间、能量或转写重合度；
4. 只有参考轨中不存在的新增语音才进入用户最终 ASR；
5. 低置信度候选保持沉默，不进入用户历史，也不触发 Memory；
6. 用户确认或拒绝候选时，沿用现有取消、暂停播放和有界队列原则。

现有实时语音的浏览器 AEC/noise suppression 可以继续作为基础，但不能据此推断电影外放、音乐外放和游戏语音已被可靠分离。媒体参考轨 AEC、转写重合检测和跨平台声学测试仍是独立工作。

### 5.3 产品降级路径

声源分离不存在对所有房间、音量和设备都可靠的软件保证，因此必须提供可预测的降级：

- **耳机自然对话**：优先支持，媒体不会经空气大幅回灌；
- **全局快捷键 / 按住说话**：外放环境第一版的默认可靠入口；
- **唤醒词后说话**：可作为中间档，但需验证媒体内容误唤醒；
- **纯文字提问**：音频条件差时始终可用；
- **不确定即不提交**：宁可漏掉一次自由插话，也不能把影视台词当作用户意图。

声纹识别只能作为附加信号，不能单独解决回声：媒体中可能出现相似声音，用户也可能跟唱、复述台词或与他人同处一室。

## 6. 响应速度

### 6.1 用户主动提问

用户说完后听到首句的初始目标为 **1.5--3 秒**，但必须通过真实设备测试确认。延迟预算可先按以下部分测量：

| 阶段 | 原型目标 | 说明 |
| --- | ---: | --- |
| 语音终点确认 | 300--700 ms | 陪伴模式不能擅自缩短现有 provider/VAD 边界 |
| 最终 ASR | 300--1000 ms | 当前仍是 whole-utterance final ASR |
| LLM 首个可用文本 | 400--1500 ms | 依赖本地/云端模型和上下文大小 |
| 首句 TTS 可播放 | 500--1500 ms | 依赖选定语音后端与流式能力 |

以上数字可以重叠，不应简单相加作为承诺。现有 SSE、`StableSentenceBuffer`、有界 TTS 队列、managed audio 和播放回执可以复用；共同体验模式不能绕过已有 generation、取消、打断和可听历史规则。

### 6.2 视觉状态必须提前准备

如果用户提问后才截屏、OCR、调用视觉模型，视觉处理会额外增加明显等待。因此共同体验会话应在后台低频维护最新结构化状态，提问时优先直接回答。

当已有状态不足时，采用“快速承认不确定 + 异步回看”的两段式策略：先给出短回应，再分析环形缓冲中的最近关键帧并补充。模型不能为了显得快速而编造刚才的内容。

### 6.3 主动评论

主动评论不追求事件发生后立即出声。更自然的做法是提前生成短候选，等待同时满足以下条件：

- 媒体对白处于空档；
- 用户没有语音候选；
- 角色当前没有未完成播放；
- 游戏不处于高强度操作或明显过场关键点；
- 候选仍与最新事件一致且没有过期；
- 发言频率、冷却和会话预算允许。

任一条件失效就丢弃候选，不排队等待稍后硬说。主动评论计时应从最后一段实际播放完成回执开始，保持与现有主动实时对话的节奏原则一致。

## 7. 主动性与角色行为

建议将“理解内容”和“决定开口”拆为两个模块。事件理解器只生成事实不完整、带置信度的会话事件；发言导演根据价值与时机决定 `speak | wait | discard`。

第一版主动候选可以只覆盖少量高价值类型：

- 明显反转后的简短反应；
- 用户连续失败后询问是否需要提示；
- 用户暂停后对刚才情节提出一个问题；
- 歌曲切换后极低频提及新曲目；
- 用户读完一节或主动选中文本后继续讨论。

默认禁止：

- 逐句评价字幕或歌词；
- 抢在人物对白中说话；
- 未经请求搜索剧情并造成剧透；
- 把模型猜测说成已确认事实；
- 因用户沉默就连续主动发言；
- 把用户打断、拒绝或静音解释为关系态度。

现有角色 prompt 和 persona 治理仍是表达权威。共同体验观察只能提供当轮内容语境，不能修改 persona、system 或 skill 规则。

## 8. 隐私、Memory 与内容边界

### 8.1 采集边界

- 必须由用户明确选择窗口或应用并开始会话；
- 采集中必须有持续可见状态和一键停止入口；
- 默认屏蔽密码、支付、系统设置和私人通讯类窗口；
- 切换到未授权窗口时停止或遮蔽采集，不自动扩大到整个桌面；
- 原始帧、媒体音频和 OCR 中间结果默认仅驻留内存并按固定 TTL 删除；
- 不在日志或诊断中记录窗口标题、应用名、作品名、字幕、歌词、截图、路径、URL、用户/角色文本或 PCM。

### 8.2 Memory 边界

共同体验内容和长期记忆必须分离：

- 作品内容、外部字幕、歌词、书页、游戏对白和模型生成的剧情摘要不自动进入 Memory；
- 用户明确表达的偏好可以沿用现有 Memory 规则形成候选，例如“我喜欢这个角色”；
- “看到第几集”“读到第几章”等进度只有用户显式开启跨会话续看或确认保存时才能持久化；
- 会话结束回顾默认只展示，不自动保存；
- 观察内容不能进入 persona、system、skill、Fresh Topics、诊断正文或无关聊天会话；
- 后续若需要共同体验专用持久化，必须先在 `roadmap-memory-brain.md` 中定义 scope、来源、删除、过期与冲突规则。

### 8.3 版权与外部服务

默认只保存短摘要和用户自己的评论，不保存或导出大段原文、连续截图或媒体音轨。若使用云端视觉、ASR 或搜索，设置页应明确哪些内容会离开本机。外部搜索只能在用户明确请求后使用，不能为了主动评论自动搜索完整剧情或攻略。

## 9. 分阶段路线

### M0：离线原型与测量

目标是回答“成本、分轨和延迟是否可接受”，不接入正式 UI。

- 分别验证 macOS / Windows 指定窗口画面与应用音频采集；
- 测量一小时影片、一小时短剧和一小时游戏的画面变化、字幕去重率与候选关键帧数量；
- 用耳机、笔记本扬声器和外接音箱测试媒体回灌；
- 测量视觉调用、最终 ASR、LLM 首字和 TTS 首音频延迟；
- 输出只有固定聚合值的实验报告，不保存内容样本到仓库或产品诊断。

通过门槛应在原型开始前给出明确数值。至少需要覆盖误把媒体当用户、漏掉用户提问、每小时视觉调用数、首句延迟和主动发言时机。

### M1：用户主动提问

- 用户选择一个窗口并开启共同体验；
- 本地检测变化、OCR 去重并维护最近事件；
- 通过全局快捷键、按住说话或文字询问最近内容；
- 只使用已有状态回答，必要时回看少量最近关键帧；
- 不主动发言，不自动写 Memory；
- 提供硬性会话预算、暂停和立即清除。

推荐先支持看片，再评估阅读；游戏和音乐需要不同事件源，不应假装一个视觉规则可以覆盖全部模式。

### M2：耳机自然语音与低频主动评论

- 在耳机场景启用自然语音候选；
- 加入媒体/角色参考轨和回声重合检测；
- 只开放少数高价值主动候选；
- 使用对白空档、候选过期、冷却和播放完成回执门控；
- 提供安静、标准、活跃档位和明确防剧透设置。

外放自由插话在声学验收通过前继续使用快捷键，不以实验能力替代可靠入口。

### M3：场景专用增强

- 游戏：稳定 UI 区域、任务/对话/失败事件和可选游戏插件；
- 音乐：跨平台媒体会话、歌词来源和播放进度；
- 阅读：选区、页码/章节和用户确认的读书笔记；
- 看片：人物/地点滚动状态、暂停后讨论和会话内防剧透线索。

每个场景独立验收成本、准确率和打扰率，不因为看片模式可用就默认开启其他模式。

### M4：可选的跨会话延续

只有完成 Memory Brain 设计后再考虑：

- 用户确认保存的观看/阅读进度；
- 用户明确表达的角色、类型、音乐或玩法偏好；
- 用户主动保存的共同体验回顾。

不得保存完整剧情资料库，也不得用外部作品内容训练或改写角色人格。

## 10. 验收维度

后续每个里程碑至少报告以下指标，不能只展示成功演示：

| 维度 | 需要回答的问题 |
| --- | --- |
| 成本 | 每小时视觉/文本/ASR/TTS 调用量和估算费用是否有硬上限？ |
| 感知 | 关键事件是否被捕获？重复字幕和无变化画面过滤率如何？ |
| 声源 | 媒体误判为用户、用户漏检和角色自回声分别有多少？ |
| 延迟 | 提问结束到 ASR、LLM 首字、首音频和完整回答分别多久？ |
| 节奏 | 主动评论有多少被用户打断、静音或立即关闭？ |
| 安全 | 未授权窗口、切窗、暂停、结束和异常退出是否立即停止采集？ |
| 数据 | 原始帧/音频是否按 TTL 清除，Memory 与诊断边界是否保持？ |
| 降级 | 无视觉 Key、模型超时、音频无法分轨时是否仍可可靠退出或改用文字？ |

建议把“用户主动关闭本次主动评论”“发言开始后一秒内被打断”和“候选生成后因时机过期而丢弃”作为文本无关的节奏指标。它们只能用于评估固定策略，不能自动修改 persona、Memory 或实时语音阈值。

## 11. 当前待验证问题

1. macOS 与 Windows 对“指定应用画面 + 指定应用音频”的实际支持、权限体验和打包要求是什么？
2. 当前 DeepSeek/Qwen-VL/本地 Ollama VL 在字幕、游戏 UI 和连续关键帧上的真实费用、TTFT 和稳定性如何？
3. 是否需要独立的本地 OCR；若需要，模型大小、语言覆盖、许可证和分发成本是否合适？
4. 媒体参考轨能否接入当前 WebView 音频链路中的 AEC，还是需要 Rust/原生音频 sidecar？
5. 外放环境下，参考轨消除与转写重合检测能达到什么误触发率？
6. “后台准备视觉状态”与 token 预算之间的最佳采样频率是什么？
7. 游戏高动态画面应采用哪些稳定事件源，是否需要对常见游戏逐个配置 UI 区域？
8. 主动评论的合适频率是否应按内容类型、用户反馈和实际播放完成动态选择？第一版应只使用固定档位，不能先假定自适应策略有效。
9. 跨会话观看/阅读进度应属于 Memory、独立会话存储，还是完全不持久化？在 Memory 路线图确认前保持会话级。

## 12. 当前推荐决策

1. 将该方向命名为“共同体验陪伴模式”，保持与普通聊天、实时通话和 Fresh Topics 的数据边界清晰。
2. 第一实现切片只做看片场景的“选择窗口 + 最近内容理解 + 用户主动提问”。
3. 外放环境默认使用全局快捷键或按住说话；耳机自然对话和自动声源判断放到后续验收。
4. 使用本地事件提取、固定滚动摘要和硬调用预算，禁止按固定秒数无条件调用视觉模型。
5. 视觉状态后台准备，回复复用现有流式文本、TTS、取消和播放回执链路。
6. 主动评论在 M1 之后单独上线，并由确定性时机门控；模型可以生成候选，但不能自行决定无限制开口。
7. 原始观察不进入 Memory 或诊断；只有用户明确表达或确认保存的个人信息才进入既有 Memory 流程。
8. 在开始产品实现前，先完成 M0 跨平台采集、成本、回声和端到端延迟原型。

## 13. M1 实现指导

### 13.1 共同体验工作区接口

在前端和 Rust/sidecar 之间保持一个窄接口；复杂的合并、分段和预算逻辑放在工作区实现内部：

```ts
type SharedExperienceWorkspace = {
  sessionId: string;
  segmentId: number;
  startedAtMs: number;
  windowId: number;
  visualTimeline: VisualEvent[];
  audioTimeline: AudioEvent[];
  chatTimeline: ChatEvent[];
  segmentSummary: string;
  rollingSummary: string;
};

addVisualEvent(event): void;
addAudioEvent(event): void;
addChatEvent(event): void;
buildContext(question): SharedExperienceContext;
rollSegment(): Promise<SegmentSummary>;
finalize(): Promise<MemoryEpisodeCandidate>;
clear(): void;
```

工作区是会话级临时状态，不得直接复用 Memory 作为实时上下文。`buildContext` 只输出固定预算的内容：整体滚动总结、当前段落总结、最近关键视觉事件、最近 ASR 事件和最近文字聊天回合。

### 13.2 上下文组织

交给 DeepSeek 的共同体验上下文必须明确标注来源：

```text
【共同体验整体总结】
...

【最近观看时间线】
[时间] 画面：...
[时间] 声音：...
[时间] 变化：...

【最近对话】
用户：...
元元：...

【当前画面】
...
```

只保留最近 2--4 条原始短事件；更早内容进入段落总结或滚动总结。提示词必须要求角色优先依据这些资料回答，不得用“电脑屏幕、房间、灯”等泛化内容代替缺失观察；不确定时明确说明没有看清。

共同体验模式保留角色身份、语气和安全规则，但关闭默认的长期 Memory recall、Fresh Topics、Web Grounding 和无关的主动话题逻辑。共同体验结束后，只有最终总结和用户明确表达的个人偏好进入既有 Memory 流程。

### 13.3 采集与推理调度

采集器和推理器必须是两个独立的有界模块：

```text
capture loop (约 3 秒画面 / 持续音频切段)
        |
        v
session spool (时间戳 + 临时文件 + 有界索引)
        |
        +--> Mage-VL worker
        +--> SenseVoice2 worker
        +--> segment summarizer / DeepSeek
```

用户输入期间只暂停模型 worker，不暂停 capture loop。输入结束后按时间顺序排空积压；若积压过多，按时间段批处理，而不是静默丢弃。当前正在播放的 VoxCPM2 优先于后台视觉/ASR 推理，但后台任务必须继续保留在 session spool 中。

每段处理完成后删除原始图片、音频和中间文件，仅保留结构化事件与摘要。30 分钟分段滚动，不停止会话；停止按钮负责最终总结、Memory episode 提交和临时目录清理。

### 13.4 第一阶段验收矩阵

按以下顺序测量，先建立基线，再叠加共同体验：

| 场景 | 本地模型 | 必测指标 |
| --- | --- | --- |
| 普通文字聊天 + 默认朗读 | VoxCPM2 | TTFA、RTF、峰值内存、窗口流畅度 |
| 画面共同体验 + 文字聊天 | Mage-VL + VoxCPM2 | 视觉耗时、TTFA、峰值内存、打字卡顿 |
| 画面/视频音频共同体验 | Mage-VL + SenseVoice2 + VoxCPM2 | ASR 延迟、时间线完整性、端到端首音频 |
| 结束并保存总结 | DeepSeek + Memory | 总结完整性、原始数据释放、episode 可召回性 |

每组至少持续 5--10 分钟；另做一组 30 分钟分段滚动测试。30 分钟墙钟 deadline 是该验收阶段的硬收尾信号：到点后不再接纳新对话轮次，允许当前在途回复完成后立即 rollover、finalize 和清理。计划的 90 轮只用于施加不均匀负载和统计实际吞吐，不作为必须拖过 deadline 才能满足的硬条件。记录视觉推理耗时、ASR 分段耗时、DeepSeek 首 token、VoxCPM2 首音频、TTS 实时率、峰值内存/显存、积压队列最大长度和聊天输入响应情况。不能只以“最终说出了话”作为通过标准。

### 13.5 失败与降级

- Mage-VL 暂时不可用：继续文字聊天和 VoxCPM2，明确标记视觉资料缺失。
- SenseVoice2 暂时不可用：保留画面时间线，禁止伪造音频内容。
- VoxCPM2 生成变慢：保留 DeepSeek 文字回复，暂停后台视觉/ASR 推理以释放资源。
- 指定窗口消失：停止采集并提示用户重新选择，不自动切换窗口。
- 聊天窗口隐藏：暂停推理与定时任务，但保留 capture spool；重新显示后继续处理。
- 用户停止共同体验：停止采集，完成最终总结；总结失败也必须清理原始媒体并允许普通聊天继续。

## 14. 文档维护规则

### 2026-09-07：问答、证据和总结基线

本轮形成的长期有效实现如下：

- 当前回答使用带来源 ID 和采集时间的有界声音/画面证据；解说视频以 ASR 为主，电影、直播和低语音游戏保留连续画面变化。浏览器外框、调试提示、推荐区和残缺语句不作为剧情事实。
- 问题与回答分别校验证据锚点、完整事实、施受关系、因果、身份和时间，允许自然表达不确定性，但不继续围绕自动测试提问器堆叠规则。
- 证据块和最终 Memory 回顾从有界原始媒体证据与真实用户讨论重新生成，不从旧摘要或角色猜测递归归纳。核对失败时，仅在存在音频或已核对证据块时保存明确标记的降级回顾。
- 历史回顾问题可拼接相邻 SenseVoice2 ASR 片段，并在电影、直播或低语音游戏中结合连续画面；采集空档和残句不补全。
- DeepSeek 生成、核对与修复请求分别计费；VoxCPM2 流式播放、spool 积压、丢弃、进程隔离和停止释放均纳入结构化验收。

macOS dev 已覆盖短时真实链路和确定性门禁，但单次演示不能证明长期内容质量。仍需持续验证摘要语义、跨句听音、峰值 GPU、30 分钟 rollover、Windows 实机和实时通话。原始对话、媒体、窗口标识及逐轮测试报告属于本地验收产物，不纳入版本库。

### 2026-09-09：主动陪看 MVP

主动陪看已作为显式、默认关闭的共同体验设置实现。频率使用固定档位：低频首次约 60 秒、后续最短 120 秒；标准首次约 30 秒、后续最短 60 秒；高频首次约 20 秒、后续最短 30 秒。档位只规定最短间隔，不按时间强制发言：解说内容需要新增可用 ASR，低语音游戏或直播需要连续画面变化。用户输入、暂停、隐藏聊天窗口、普通回复、实时通话和 TTS 会抑制或取消候选；VoxCPM2 播放期间仍持续采集，Mage-VL 推理结束暂停后按有界 spool 补处理。

主动评论使用独立隐藏触发，要求像一起观看时分享刚发现的内容，而不是回答问题、反问用户、审计声画或复述资料来源。普通用户问答的工作区提示也改为先自然接话、再直接回答和补充判断，保留简单事实问题首句自包含的既有契约。生成或核对失败的候选会消费本次证据并进入冷却，不再对同一证据连续重试；用户活动导致的取消不消费证据。

暂停或结束共同体验是严格的输出边界：即使主动生成任务已经结束，只剩流式 TTS 正在播放或排队，也必须立即停止当前音频并作废后续分句。进入共同体验时同时撤销普通聊天的空闲主动分享计时器，共同体验期间的输入不得重新安排该计时器，结束后也不补发跨模式主动话题；只有后续新的普通聊天活动才重新开始空闲计时。对应回归覆盖 runner 已结束时的强制清音、无主动任务时不误伤普通朗读，以及空闲计时器的模式隔离。

macOS 当前源码 debug binary 使用用户指定的 Chrome 视频窗口完成 84.9 秒真实链路验收，后端为 DeepSeek Flash、Mage-VL、SenseVoice2 和 VoxCPM2。主动评论成功 2 次，间隔约 29 秒，均完成流式 TTS；24 张画面和 7 段音频全部处理，spool 峰值 2、丢弃 0，隔离检查 36 次无安装版进程。停止时 capture、workspace 和 spool 均完整释放，Memory 写入成功。最终摘要本轮语义核对失败后保存了明确标记的降级回顾，因此不能把这次记录视为最终摘要内容质量通过。发布前仍需补 Windows 实机，以及用户在设置页手动切换开关/三档频率的交互验收。
